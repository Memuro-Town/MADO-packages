# sample-data — 外部レビュー・検証用の完全架空データセット

MADO（`hub` / `form` / `care` / `move`）を外部からレビュー・検証するための、**完全に架空の住民データセット**。

**このディレクトリのデータに、実在の住民情報は一切含まれていない。** 実データを匿名化・サニタイズしたものでもない。氏名・住所・自治体名・団体コード・各種番号のすべてが、この検証用途のために新規に作った架空の値である。

> このデータセットは `Memuro-Town/MADO` [Issue #4](https://github.com/Memuro-Town/MADO/issues/4)「hub/form/care/move の外部レビュー用に完全架空の検証データセットを用意したい」での議論を実装したもの。ディレクトリ構成は同 Issue で [@to4kawa](https://github.com/to4kawa) 氏が提案した形をそのまま採っている。

## なぜ「実データの匿名化」ではなく「完全架空」なのか

Issue #4 では、外部レビューのためのデータの用意のしかたとして、実データを匿名化・サニタイズする方法と、最初から架空データを作る方法が比較された。結論として後者を採っている。理由は次のとおり。

1. **再識別リスクを構造的に持ち込まない。**
   住民データには住所・世帯構成・異動履歴・続柄・外字・自由記述が含まれる。匿名化した場合でも、これらの組み合わせから個人が特定されうるかを毎回検討する必要がある。最初から架空データであれば、その検討自体が不要になる。

2. **「本当に消せているか」の確認コストがかからない。**
   匿名化方式では、公開するたびに変換漏れがないかを確認しなければならない。架空データであれば、確認すべきは「値が架空であること」だけで、これは機械的に検査できる（[`scripts/verify-sample-data.mjs`](scripts/verify-sample-data.mjs)）。

3. **検証したいパターンを意図して作れる。**
   実データの抜粋では、死亡者を含む世帯・外国人住民世帯・転出予定のレコードといった、`care` / `move` の検証に必要なパターンが都合よく揃うとは限らない。架空データなら必要なパターンを列挙して作れる。

4. **実データの匿名化手順を決めなくてよい。**
   匿名化手順の策定は Issue #4 の範囲外とされている。架空データはその決定を待たずに用意できる。

## ディレクトリ構成

```
sample-data/
├── csv/                              # 人間がレビューしやすい主資料
│   ├── resident_table.csv            #   住民テーブル（27件 / 122列 / 日本語カラム名）
│   └── household_patterns.csv        #   世帯パターンの索引（DBには投入しない）
├── prisma/                           # schema.prisma 対応の seed データ
│   └── resident_table.seed.json      #   DDLの型に合わせた JSON（空欄は null）
├── scripts/                          # 生成・投入・検査スクリプト（Node.js / 依存パッケージなし）
│   ├── generate-sample-data.mjs      #   世帯定義から csv/ と prisma/ を生成
│   ├── load-postgres.mjs             #   CSV → PostgreSQL（hub の標準経路）
│   ├── csv-to-sql.mjs                #   CSV → INSERT文（PostgreSQL / SQLite）
│   ├── verify-sample-data.mjs        #   生成済みファイルの検査
│   └── lib/csv.mjs                   #   最小CSVパーサ
└── README.md                         # このファイル
```

`csv/` が主資料で、`prisma/` はそこから生成される派生物である。**データを直すときは `scripts/generate-sample-data.mjs` の世帯定義を直して再生成する。** CSV や JSON を直接編集すると、次の再生成で失われる。

## データの単位 — 住民テーブル1本で持つ

Issue #4 のたたき台では、住民・世帯・世帯員・住所・異動履歴・手続きケースをそれぞれ別テーブルに分ける案が示された。その後の議論で、芽室町の実際の構成が次のようになっていることが共有されたため、このデータセットは**住民テーブル1本**で構成している。

- 基本は住民テーブルで管理し、**世帯番号がレコードごとに入る**
- **異動履歴・手続きケースは住民基本台帳側で管理しており、MADO では持たない**

たたき台の各テーブルは、このデータセットでは次のように住民テーブルのカラムへ畳み込まれている。

| Issue #4 たたき台のテーブル | このデータセットでの扱い |
|---|---|
| `sample_residents` | `resident_table` の本体（`氏名` `氏名_フリガナ` `生年月日` `性別表記` `住民状態` など） |
| `sample_households` | `世帯番号` `世帯主氏名`（世帯レコードは持たず、住民レコードに世帯番号が入る） |
| `sample_household_members` | `続柄コード1` `続柄表記` `記載順位` |
| `sample_addresses` | `住所_都道府県` `住所_市区郡町村名` `住所_町字` `住所_番地号表記` `住所_方書` `住所_郵便番号` `住所_町字コード` |
| `sample_resident_movements` | **持たない**（住基側の管理。転入前住所・転出先住所は住民レコードの現在値としてのみ保持） |
| `sample_procedure_cases` | **持たない**（住基側の管理） |

たたき台では自治体名を「雪見町」、団体コード `019999` としていたが、このデータセットでは実在の団体コード体系との誤認を避けるため、**`サンプル県サンプル市` / 団体コード `999999`** に統一した。転入元・転出先には架空の他団体 `ダミー県ダミー市` / `999998` を使っている。どちらも実在しない値である。

### 氏名について

氏は十干（甲・乙・丙・丁・戊・己・庚・辛・壬・癸）を用いた架空姓のみを使っている。日本の法律文書で仮名の当事者を表すときの慣行に合わせたもので、実在の姓との一致を避けるためである。外国人住民世帯は `サンプル　テスト` / `SAMPLE TEST` のように、名前・国名（`サンプル国`）・国名コード（`999`）のいずれも実在しない値にしている。特定の国を想起させないことを意図している。

## 個人番号を含めていないこと

**このデータセットには `個人番号`（マイナンバー）のカラムを持たせていない。** 値が空なのではなく、CSV・JSON・DDL のいずれにも列そのものが存在しない。

理由は Issue #4 での合意事項であることに加えて、次のとおり。

- 個人番号は法令上の取扱いが特別に厳格であり、**値が架空の合成値であっても、サンプルデータに列として存在すること自体が誤用・誤解を招く**。
- 「この列に検証用の値を入れてよい」という前例を作らないほうが、外部からのコントリビューションを受け付けるうえで安全である。

同じ判断は `packages/hub` 側でも取られており、[`packages/hub/docs/database-requirements.md`](../packages/hub/docs/database-requirements.md) に「本リポジトリで意図的に持たせない項目」として記載されている。

[`scripts/verify-sample-data.mjs`](scripts/verify-sample-data.mjs) は、個人番号に相当する列が混入していないことを毎回機械的に検査する。

### 意図的に値を持たせていない項目

次の列は、住民テーブルの構造を示すために**列としては存在させるが、値はすべて空**にしている。

| カラム | 空にしている理由 |
|---|---|
| `基礎年金番号` | 他制度の識別番号であり、架空値であっても検証用データに具体的な値を置く必要がない |
| `在留カード等番号` | 同上 |

いずれも `packages/hub` のアプリケーション側で閲覧可能カラムの許可リストから除外されている列でもある（`packages/hub/lib/permissionGroups.ts` の `RESIDENT_BASIC_COLUMNS`）。

### 架空値を入れている識別番号

| カラム | このデータセットでの値 |
|---|---|
| `住民票コード` | `99900000001` 以降の連番。実在しない番号帯 |
| `宛名番号` | `1`〜`27` |
| `世帯番号` | `100`〜`1100`（100刻み） |
| `操作者ID` | すべて `SAMPLE`。実在の職員IDではない |

### 値の意味を定義していない項目

次の列には形式を満たすだけの仮の値（多くは `99`）を入れている。**このデータセットではコード値の意味を定義していない。** 各団体のコード体系に読み替えて使うこと。

`異動事由` / `異動区分` / `記載等の種別` / `記載の事由` / `届出番号` / `年金資格種別` / `国籍等_国名コード` / `在留資格等コード`

一方で、次の列の値は [`packages/hub/docs/database-requirements.md`](../packages/hub/docs/database-requirements.md) に記載されている定義に合わせている。

- `住民種別` — `1`: 日本人、`2`: 外国人
- `住民状態` — `1`: 住民、`2`: 転出者、`3`: 死亡者、`9`: その他消除者
- `続柄コード1` — `02` 世帯主 / `11` 夫 / `12` 妻 / `20` 子 / `51` 父 / `52` 母 / `74` 弟 / `96` 縁故者 / `99` 同居人
- 各種年月日 — `YYYY-MM-DD`
- 郵便番号 — 全角7桁

## ファイル形式の決めごと

### CSV は BOM 付き UTF-8 / 改行 LF

| 項目 | 決めごと | 理由 |
|---|---|---|
| 文字コード | **UTF-8（BOM あり）** | `csv/` の主な読み手は、庁内で Excel を使ってレビューする自治体職員である。Windows の Excel は BOM のない UTF-8 CSV をダブルクリックで開くと、環境によっては Shift_JIS と誤認して日本語が文字化けする。文字化けした表を見せられた側は「データの中身」ではなく「開き方」の話から始めることになり、レビューの目的を損なう。BOM を付けるとダブルクリックで正しく開ける。 |
| 改行 | **LF** | リポジトリの `.gitattributes` が `* text=auto eol=lf` を指定しており、リポジトリ内はLFで保存される。差分を素直に読めるようにするため、生成時点からLFで出力している。 |

BOM は素朴なCSVパーサにとっては先頭列名を汚す異物になるため、このディレクトリのスクリプトは `scripts/lib/csv.mjs` で必ず BOM を除去してから解析する。**外部のツールで読む場合も、先頭の `U+FEFF` を除去すること。**

### PostgreSQL を主とし、SQLite も投入できる形で出す

Issue #4 では「CSV → SQLite / PostgreSQL 投入用スクリプト」とされていた。現時点の状況は次のとおり。

- `hub` は **PostgreSQL へ移行済み**（`packages/hub/prisma/schema.prisma` の datasource は `postgresql`）
- `form` / `care` / `move` は現行モデルが SQLite

そこで **PostgreSQL を主たる投入先**とし、SQLite は「同じ CSV から INSERT 文を出力して流し込む」経路で対応している。

- PostgreSQL — [`scripts/load-postgres.mjs`](scripts/load-postgres.mjs) が `@prisma/client` 経由で直接投入する（`hub` の `npm run seed` と同じ経路）
- SQLite — [`scripts/csv-to-sql.mjs`](scripts/csv-to-sql.mjs) `--dialect sqlite` が `.sql` を出力し、`sqlite3` CLI で流し込む

SQLite 側に専用のドライバを使ったスクリプトを置いていないのは、`better-sqlite3` などのネイティブ依存を新たに追加すると、オフラインの閉域網でのビルドが難しくなるためである。`.sql` を出す方式なら追加の依存パッケージが要らない。`form` / `care` / `move` がこのリポジトリに追加された時点で、専用スクリプトが必要かどうかを改めて検討する。

なお、スクリプトはいずれも**値をすべて文字列リテラルとして出力する**。PostgreSQL / SQLite のどちらも INSERT 時に列の型へ暗黙変換するため、`packages/hub/prisma/init.sql`（多くの列が `TEXT`）と `packages/hub/prisma/dev_init.sql`（`INTEGER` / `BIGINT` を含む）のどちらの DDL で作った表にも投入できる。

## 生成方法

`csv/` と `prisma/` の中身は、[`scripts/generate-sample-data.mjs`](scripts/generate-sample-data.mjs) 内の世帯定義から決定論的に生成される。乱数は使っていないので、何度実行しても同じ結果になる。

```bash
node sample-data/scripts/generate-sample-data.mjs
```

生成時に「個人番号列がないこと」「団体コードが架空値だけであること」「世帯ごとに世帯主が1人であること」「記載順位が連番であること」などを検査し、1つでも失敗するとファイルを書き出さずに終了する。

データを増やしたり変えたりするときは、スクリプト内の `HOUSEHOLDS` に世帯を足して再生成する。列を増減するときは `COLUMNS` を `packages/hub/prisma/dev_init.sql` と一致させること。

### 検査だけを実行する

```bash
node sample-data/scripts/verify-sample-data.mjs
```

コミット済みの CSV / JSON を対象に、上記の検査に加えて `packages/hub/prisma/dev_init.sql` との列構成の一致も確認する（列構成が食い違う場合は警告として出力する）。レビュー時や CI で実行することを想定している。

依存パッケージはなく、外部ネットワークにもアクセスしない。Node.js 標準モジュールだけで動く。

## 投入方法

### PostgreSQL（`hub`）

`hub` の開発環境の立ち上げ方は [`packages/hub/README.md`](../packages/hub/README.md) と `docs/DEVELOPMENT.md` を参照。PostgreSQL が起動していて `resident_table` が作られている状態から始める。

```bash
# @prisma/client と .env(DATABASE_URL) を解決するため packages/hub から実行する
cd packages/hub
node ../../sample-data/scripts/load-postgres.mjs
```

| オプション | 動作 |
|---|---|
| なし | 既存行を残したまま27件を追加する |
| `--truncate` | `resident_table` を空にしてから投入する |
| `--dry-run` | DBに接続せず、実行される INSERT 文を標準出力に表示する |

> ⚠️ `--truncate` は `resident_table` の全行を削除する。**実データの入った環境では絶対に実行しないこと。**

`hub` に同梱されている `packages/hub/prisma/seed.js`（`npm run seed`）は、`hub` 単体の開発用の別のダミーデータである。このデータセットとは独立しており、混ぜて使うと宛名番号が衝突する可能性がある。どちらか一方を使うこと。

### SQL ファイルを経由する（PostgreSQL / SQLite 共通）

`psql` や `sqlite3` の CLI しかない環境向け。

```bash
# PostgreSQL
node sample-data/scripts/csv-to-sql.mjs --dialect postgres > sample-data.sql
psql "$DATABASE_URL" -f sample-data.sql

# SQLite（form / care / move の現行モデル向け）
node sample-data/scripts/csv-to-sql.mjs --dialect sqlite > sample-data.sql
sqlite3 <DBファイル> < sample-data.sql
```

`--truncate` を付けると、先頭に既存行の削除（PostgreSQL: `TRUNCATE`、SQLite: `DELETE FROM`）が入る。生成される `.sql` はトランザクションで囲まれている。

投入先の `resident_table` は事前に作っておくこと。PostgreSQL 用の DDL は `packages/hub/prisma/init.sql`（`docker compose` が初回起動時に実行する）と `packages/hub/prisma/dev_init.sql` にある。

### Prisma seed データ（JSON）

[`prisma/resident_table.seed.json`](prisma/resident_table.seed.json) は、CSV と同じ27件を `packages/hub/prisma/dev_init.sql` の型定義に合わせた JSON にしたもの。`INTEGER` / `BIGINT` の列は数値、それ以外は文字列、空欄は `null` になっている。独自の投入スクリプトを書く場合や、Prisma のモデル定義との突き合わせに使う。

## このデータセットが扱わないこと

Issue #4 で範囲外として明示された事項を、そのまま引き継ぐ。**このデータセットは以下を目的とするものではない。**

- **本番接続仕様を決めること**
- **住民基本台帳ネットワークシステムの接続仕様を再現すること**
- **住民記録システム全体を再実装すること**
- **MADO `hub` の正式スキーマを確定すること**
- **実データの匿名化手順を定めること**

加えて、このディレクトリの実装上、次も扱っていない。

- **異動履歴・手続きケースのデータ** — 住民基本台帳側で管理されており MADO では持たないため、テーブルもデータも用意していない。転入前住所・転出先住所は、住民レコードの現在値としてのみ保持している。
- **`care` のおくやみテーブル、`care` / `move` の戸別端末テーブル** — このリポジトリは現時点で `packages/hub` のみを収めており、住民テーブル以外のサンプルは用意していない。
- **コード値の正式な意味の定義** — 上記「値の意味を定義していない項目」を参照。
- **標準仕様書との正式な対応関係** — 上記「カラム対応表（参考）」の注意書きを参照。

あくまで、外部レビューと検証をしやすくするための仮のデータセットである。
