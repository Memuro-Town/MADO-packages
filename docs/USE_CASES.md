# 現場での使い方（hub）

初めてこのリポジトリを見る人向けに、`hub` が窓口でどう使われ、なぜこの形になっているのかを書く。

---

## 1. 基本の流れ

窓口業務で使う画面は2つしかない。`/login`（ログイン）と `/`（検索・出力）だけ。（`admin` ロールのユーザーだけが使える管理画面は別にあるが、窓口業務では触らない。[packages/hub/README.md](../packages/hub/README.md#管理画面) を参照）

```
ログイン
  ↓
検索欄に1つだけ入力（氏名／フリガナ／生年月日／宛名番号）
  ↓
候補一覧から対象者を選ぶ
  ↓
出力したい項目にチェックを入れる（＋必要なら世帯員も選ぶ）
  ↓
「クリップボードにコピー」→ Excel に貼り付け
                    または「CSV」でファイル保存
```

窓口で住民と話しながら操作する場面と、自席で1件だけ手早く調べたい場面の両方を想定しているため、**ページ遷移を挟まない**。検索から出力まで1画面で完結する。

---

## 2. 典型的な使われ方

### ケース1: 通知や案内の宛名を作る

対象者を検索し、「氏名」「郵便番号」「住所」にチェック（この3つは最初から選択されている）。コピーして Excel の差し込み用シートに貼る。

2人目以降も同じように貼っていくと1行ずつ追加される。**列名を含めるチェックは1回出力すると自動でオフになる**ので、2件目から列名が混ざらない。

### ケース2: 世帯構成の確認

対象者を検索して詳細を開くと、同一世帯の構成員が `記載順位` の順に一覧表示される。出力に含める世帯員を個別に選べるので、必要な人だけを1行に横並びで出せる。生年月日・年齢を付けるかどうかも切り替えられる。

本籍・戸籍筆頭者も項目として選択できる。

### ケース3: 定型項目にない情報が必要になったとき

住民テーブルには100列以上ある。画面の定型項目には出していない列も、「カスタム列」のドロップダウンから最大5つまで選んで出力に追加できる。

ドロップダウンに出てくるのは**許可リストに載っている列だけ**。基礎年金番号・在留カード等番号などはリストに含めていないため、そもそも選択肢に現れない。個人番号（マイナンバー）にいたっては、DBのスキーマにもサンプルデータにも列を持たせていない。何を出せるようにするかは導入時に決める（[ARCHITECTURE.md](ARCHITECTURE.md#権限設計の現状と限界)）。

## 3. 設計の「なぜ」

### なぜ検索欄が1つなのか

「氏名で検索」「生年月日で検索」とタブを分けると、職員は毎回どのタブかを選ぶ必要がある。窓口で住民を待たせながらの操作でこれは邪魔になる。

そこで入力された文字列から検索方法を自動判定する形にした。

| 入力 | 判定 |
|---|---|
| 数字以外を含む | 氏名・フリガナ |
| 7桁数字（8,000,000未満） | 和暦の生年月日 |
| 8桁数字（19000101〜20399999） | 西暦の生年月日 |
| その他の数字 | 宛名番号 |

### なぜ和暦7桁で入力できるのか

行政の現場では生年月日を「元号コード1桁＋年2桁＋月2桁＋日2桁」の7桁で扱う場面が多い（例: `4050101` = 平成5年1月1日）。西暦に読み替えてから入力させると、読み替えの手間と間違いが増える。そのまま打てるようにした。

先頭1桁は `1:明治 2:大正 3:昭和 4:平成 5:令和`。

### なぜひらがなで検索できるのか

DBのフリガナはカタカナで格納されている。しかし入力しているのは職員であり、住民の名乗りを聞きながら打つときにいちいち変換モードを切り替えるのは負担になる。ひらがな入力を内部でカタカナに変換して両方を照合している。

姓と名の間のスペース（半角・全角）も無視する。DBの格納形式と職員の入力が食い違っても引っかかるようにするため。

### なぜ結果が50件までなのか

「佐藤」のような姓で検索すると数百件が返る。全件を返しても職員は目視で選べないし、窓口の待ち時間になるだけである。50件で打ち切り、**絞り込める情報（生年月日や宛名番号）で再検索してもらう**方が速い。

### なぜ転出者・死亡者のバッジが目立つのか

検索結果には転出者・死亡者・消除者も出る。同姓同名や世帯内の類似氏名で**別人を選んでしまう事故**を防ぐ必要がある。バッジは意図的に強い配色（`★★転出者★★` など）にしてある。

MADO の配色規定では強調に赤を使わないが、**ステータス警告バッジだけは例外**としている。

### なぜ「決まった帳票」ではなく項目選択なのか

必要な項目は業務ごとに違う。おくやみ窓口では本籍・筆頭者・世帯員が要るが、通知の宛名では氏名と住所だけでよい。帳票を固定すると業務の数だけ様式を作り込むことになり、現場の変更要望のたびに開発が必要になる。

項目をチェックボックスで選ぶ形にしたことで、**新しい用途が出てきても職員だけで対応できる**。

### なぜクリップボードが主でCSVが従なのか

現場の様式はほとんどが Excel である。ファイルをダウンロードして開いて貼り直すより、コピーして貼る方が手数が少ない。タブ区切りで出しているのは Excel がそのままセルに分割してくれるため。

CSVは、ファイルとして残したい場合や他システムに取り込む場合の逃げ道として用意している（BOM付きUTF-8。Excel で開いても文字化けしない）。

### 職員アカウントの登録・無効化

`admin` ロールのユーザーは管理画面（`/admin/users`）からアカウントを登録・無効化できる。サーバ上のCLI（`scripts/create-user.mjs` / `disable-user.mjs`）も引き続き使えるが、これは初期管理者の作成時や、画面が使えない場合の復旧手段としての位置づけである。

無効化はレコードを削除せず `is_active` を落とすだけにしている。「いつ誰のアカウントがあったか」の記録を消さないため。

管理画面の操作（登録・権限変更等）はすべて `admin_audit_log` テーブルに記録される。住民データの閲覧記録（`audit_log`）とは性質・点検頻度・閲覧者が異なるため、意図的にテーブルを分けている。

### なぜセッションに2種類の期限があるのか

- **無操作タイムアウト（10分）** — 最終操作から10分でセッションが失効する。操作のたびに延長される（スライディング方式）。離席したPCで別の職員がそのまま操作できてしまうのを防ぐため
- **絶対タイムアウト（12時間）** — 最初のログインから12時間で、操作を続けていても必ず失効する。窓口の勤務時間をまたいで再ログインを強いると業務の途中で操作が止まるため、1営業日をカバーしつつ翌日には切れる長さにしている

`hub` はバックヤードでの職員個人PCでの使用を想定している。共用PCで使う場合は、操作者を限定する（＝いま誰が使っているかを常に明確にする）観点から、無操作タイムアウトをより短く設定することを想定している。

## 4. 導入時に決める必要があること

`hub` を他自治体で使う場合、少なくとも以下は導入側で決める。

| 項目 | 内容 |
|---|---|
| 住民データの投入方法 | 住民基本台帳システムからどう `hub` のDBに持ってくるか。`hub` アプリ自体はデータの取り込み機能を持たない。芽室町での実装例は [`tools/csv_import`](../tools/csv_import/README.md) を参照 |
| 更新頻度 | 日次か、週次か。どの時点のデータを見ていることになるのかを職員に周知する必要がある |
| カラム名のマッピング | `columns.json` を自庁の出力仕様に合わせる（[packages/hub/README.md](../packages/hub/README.md)） |
| 権限グループの設計 | `lib/permissionGroups.ts` に定義された「基本グループ」1種類を、自庁の部署・業務単位に合わせて分割するかどうか（[ARCHITECTURE.md](ARCHITECTURE.md#権限設計の現状と限界)） |
| 権限の付与運用 | 管理画面（`/admin/users`）からの期限つき付与・臨時例外の仕組みはある。誰を `admin` ロールにするか、期限の既定値（年度末）を自庁の人事異動サイクルに合わせるかどうかの判断が必要 |
| 閲覧記録の扱い | 検索・住民詳細閲覧・世帯閲覧・カスタム列取得は `audit_log` に記録される。出力操作（クリップボードへのコピー・CSV保存）は記録されない。既に稼働しているDBには `psql -f prisma/auth_init.sql` の手動適用が必要（[ARCHITECTURE.md](ARCHITECTURE.md#権限設計の現状と限界)） |
| 監査ログの保持・アクセス制御 | `audit_log` には検索クエリなど個人情報が平文で入るため、テーブル自体が個人情報を含む。誰が参照できるか、どれだけ保持するか、削除・アーカイブをどう運用するかは導入自治体が定める必要がある |

出力操作が監査ログに残らない点・権限グループが現状1種類しかない点は、隠さずに書いておく `hub` の弱点である。設計から相談したい領域なので、Issue での議論を歓迎する。
