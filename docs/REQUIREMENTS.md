# 業務要件定義書（hub）

`hub` が何を解決するためのシステムなのかと、接続先となる住民データベースに求める要件をまとめる。

---

## 1. 解決したい課題

### 1-1. 職員による手入力の転記

窓口業務では、住民基本台帳システムの照会画面を見ながら、氏名・住所・生年月日・世帯主名などを Excel の様式や各種帳票に手で打ち直す場面が繰り返し発生する。

- 1件あたりの入力は数分でも、日に何十件も積み上がると無視できない時間になる
- 目視での書き写しは打ち間違いが起きる。特に住所の番地・方書、旧字体を含む氏名で発生しやすい
- 世帯全員分を書き出す作業は、人数分だけ同じことを繰り返す

`hub` は、住民を検索して必要な項目にチェックを入れ、クリップボードにコピーするかCSVで落とすところまでを1画面で完結させる。

### 1-2. 「住民が名前を55回書く」問題への接続

転入・婚姻・国保・障害者手帳などの手続きが重なると、住民は同じ情報を何度も書かされる。MADO 全体としては、住民情報を一度読み込んで各申請書へ自動転記することでこれを解消する（`form` パッケージ）。

`hub` はその**入口**にあたる。住民情報を検索・特定して他パッケージに渡す共通土台であり、`form` / `care` / `move` はいずれも `hub` に依存する。

### 1-3. 出力様式が現場ごとに違う

必要な項目は業務によって違う。おくやみ窓口では本籍・戸籍筆頭者・世帯員が要る一方、通知の宛名印刷では氏名と住所だけでよい。「決まった帳票を出す」のではなく「**必要な項目を職員がその場で選べる**」形にした理由はここにある。

## 2. 利用者と利用環境

| 項目 | 内容 |
|---|---|
| 利用者 | 窓口業務に従事する職員（アカウントを付与された者のみ） |
| 端末 | 庁内ネットワークに接続されたPC。ブラウザは Chrome / Edge |
| ネットワーク | 閉じた庁内ネットワーク。インターネットからは到達できない。芽室町では三層分離のうち**個人番号利用事務系**に設置している |
| 同時利用 | 窓口の担当者が同時に利用することを想定 |

インターネット公開は想定していない。詳細は [ARCHITECTURE.md](ARCHITECTURE.md#ネットワーク上の想定) を参照。

| # | 要件 | 実装状況 |

| F-2 | 氏名・フリガナ・生年月日・宛名番号のいずれでも住民を検索できる | 実装済み（入力欄1つで自動判別） |
| F-3 | フリガナはひらがなで入力しても検索できる | 実装済み |
| F-4 | 生年月日は和暦7桁・西暦8桁のどちらでも入力できる | 実装済み |

| F-6 | 転出者・死亡者・消除者は一目で区別できる | 実装済み（警告バッジ） |
| F-7 | 同一世帯の構成員を一覧し、出力対象を個別に選べる | 実装済み |
| F-8 | 出力する項目を職員がその場で選択できる | 実装済み |
| F-9 | 定型項目にない列も、許可された範囲で追加できる | 実装済み（カスタム列・最大5列） |
| F-10 | Excel に直接貼り付けられる形式で出力できる | 実装済み（タブ区切り） |
| F-11 | CSVファイルとしても保存できる | 実装済み（BOM付きUTF-8） |
| F-12 | 職員アカウントを登録・無効化できる | 実装済み（CLI） |
| F-13 | 自治体ごとに異なるDBカラム名に、コード修正なしで対応できる | 実装済み（`columns.json`） |
| F-14 | 誰がいつ誰の情報を閲覧したか記録する | 実装済み（`audit_log`。管理画面の操作は `admin_audit_log`、改ざん検知は `daily_digests`）。ただし**出力操作（クリップボードへのコピー・CSV保存）は記録されない** |
| F-15 | 部署・職務に応じて閲覧できる範囲を変える | 一部実装（権限グループによる列単位の制御と、期限つきの個人単位の付与は実装済み。ただし定義済みグループは「基本グループ」1種類のみで、業務単位の作り分けと行単位の制限は未対応。[ARCHITECTURE.md](ARCHITECTURE.md#権限設計の現状と限界) 参照） |

## 4. 非機能要件

| 区分 | 要件 |
|---|---|
| 性能 | 検索結果は最大50件で打ち切る。窓口対応中の待ち時間を作らないため |
| 可用性 | 停止しても窓口業務は従来どおりの手入力で継続できること（業務停止に直結させない） |
| 保守性 | DBのカラム構成が変わっても、設定ファイルの差し替えで追随できること |
| オフライン性 | 外部CDN・外部APIに依存しないこと。ビルド・実行がインターネット接続なしで完結すること |
| データ更新 | 住民データはこのシステムから**書き換えない**（参照専用） |

`hub` は住民データを一切更新しない。すべてのクエリは `SELECT` で、更新・削除の経路を持たない。

---

## 5. 住民データベースの要件

`hub` が接続する住民テーブルに求めるカラム定義。自治体の住民基本台帳システムからの出力仕様に依存するため、**カラム名は `columns.json` で読み替える**ことを前提とする（[packages/hub/README.md](../packages/hub/README.md) 参照）。

以下の節では、同梱のサンプルDDL（`packages/hub/prisma/init.sql`）と `columns.json` の既定値に実際に使われている列名で記述する。`packages/hub/docs/database-requirements.md` にも住民記録システム標準仕様書寄りのカラム定義メモがあるが、そちらは検討段階のものを含み、一部の列名の表記が同梱DDLと一致していない（`転入前_都道府県` / `本籍_地番号` など）。**実装が参照する列名はこの節と `columns.json` を基準にすること。**

### 5-1. 識別・状態

| カラム | 型 | 説明 | 値の定義 |
|---|---|---|---|
| 宛名番号 | INTEGER | 住民の一意識別コード。検索・詳細取得の主キー | 整数 |
| 個人履歴番号 | — | 住民の履歴を一意に識別する番号 | — |
| 世帯番号 | INTEGER | 世帯の識別コード。世帯員一覧の絞り込みキー | 整数 |
| 住民種別 | — | 住民の国籍種別 | 1: 日本人、2: 外国人 |
| 住民状態 | — | 住民の現在の状態 | 1: 住民、2: 転出者、3: 死亡者、9: その他消除者 |

> **型の注意:** `宛名番号` と `世帯番号` は、APIが入力値を `parseInt` してから整数として問い合わせる（`app/api/residents/[id]/route.ts`・`app/api/households/[id]/route.ts`）。この2列だけは**整数型で保持すること。** TEXT型のままだとPostgreSQL側で型不一致になる。それ以外の列は TEXT でも動く（`住民状態` などのコード値はアプリ側で数値に変換して判定している）。
> なお同梱のサンプルDDL `prisma/init.sql` は `世帯番号` を TEXT で定義しており、この要件と一致していない（[ARCHITECTURE.md](ARCHITECTURE.md#サンプルddlの既知の不一致)）。自庁のDDLを起こす際はこちらの要件に従うこと。

### 機微な項目の扱い

| 項目 | 本リポジトリでの扱い |
|---|---|
| `個人番号`（マイナンバー） | **検証用スキーマ・サンプルデータのいずれにも列として持たせていない** |
| `基礎年金番号`・`在留カード等番号` | 列としては存在するが、`lib/permissionGroups.ts` の権限グループの対象列に含めていない。画面・APIからは取得できない |
| `住民票コード` | 許可リストに**含めている**（意図的な設定） |

`個人番号` は、値が架空の合成値であっても、法令上の取扱いが特別に厳格な項目をサンプルデータに列として置くこと自体が誤用・誤解を招くという判断で持たせていない。住民記録システム標準仕様書に基づく実装で当該項目が必要になる場合は、各団体の責任において、法令上・運用上の要件を満たしたうえで追加すること。

この扱いは [Memuro-Town/MADO#4](https://github.com/Memuro-Town/MADO/issues/4) で合意した内容にもとづく。検証用データセット全体の設計は同 Issue で継続して議論している。

許可リストの考え方と現状の限界は [ARCHITECTURE.md](ARCHITECTURE.md#権限設計の現状と限界) を参照。

### 5-2. 氏名

| カラム | 説明 |
|---|---|
| 氏名 | 氏名（検索対象） |
| 氏名_フリガナ | フリガナ（検索対象） |
| 氏名_フリガナ確認状況 | フリガナの確認状態を示すフラグ |
| 氏_日本人 / 名_日本人 | 姓・名の分割 |
| 氏名_外国人ローマ字 | 外国人住民のローマ字表記 |

### 5-3. 日付

| カラム | 型 | 形式 |
|---|---|---|
| 生年月日 | DATE / TEXT | `YYYY-MM-DD` または `YYYY/MM/DD`（例: `2026-05-19`） |
| その他の各種年月日 | DATE / TEXT | 同上 |

和暦での表示・和暦入力での検索はアプリ側（`lib/date.ts`）で変換する。DBには西暦で格納されている前提。

### 5-4. 世帯・続柄

| カラム | 説明 |
|---|---|
| 続柄コード | 世帯内の続柄（コード） |
| 続柄表記 | 世帯内の続柄（表示名） |
| 世帯主氏名 | 世帯主の氏名 |
| 記載順位 | 世帯員一覧の並び順（昇順ソートに使用） |

続柄コードの体系（参考）:

| コード | 続柄 | | コード | 続柄 |
|---|---|---|---|---|
| 02 | 世帯主 | | 51 | 父 |
| 11 | 夫 | | 52 | 母 |
| 12 | 妻 | | 71 | 兄 |
| 13 | 夫（未届） | | 74 | 弟 |
| 14 | 妻（未届） | | 81 | 姉 |
| 20 | 子 | | 84 | 妹 |
| | | | 96 | 縁故者 |
| | | | 99 | 同居人 |

### 5-5. 住所

| カラム | 説明 |
|---|---|
| 住所_都道府県 / 住所_市区郡町村名 | 都道府県・市区郡町村名 |
| 住所_町字 | 町字（丁目まで） |
| 住所_番地号表記 | 番地・号 |
| 住所_方書 | 方書（建物名・部屋番号等） |
| 住所_郵便番号 | 郵便番号 |
| 地区管理コード1 | 行政区名 |

完全な住所は `町字` + `番地号表記` + `方書` を結合して得る。

### 5-6. 転入前住所

転入前住所の格納方法は自治体のシステムによって2パターンある。

**パターンA：分割記載**

| カラム | 説明 |
|---|---|
| 転入前住所_都道府県 | 都道府県名 |
| 転入前住所_市区郡町村名 | 市区郡町村名 |
| 転入前住所_町字 | 丁目まで |
| 転入前住所_番地号表記 | 番地・号を別カラムに記載 |

**パターンB：町字にすべて記載**

| カラム | 説明 |
|---|---|
| 転入前住所_都道府県 | 空または省略 |
| 転入前住所_市区郡町村名 | 空または省略 |
| 転入前住所_町字 | 都道府県〜番地まですべてを含む |
| 転入前住所_番地号表記 | 空または省略 |

> 住所の完全表記は4カラムを結合して得る。パターンBでは `転入前住所_町字` 単独で完全住所となる。**どちらのパターンかは導入時に確認が必要。**

### 5-7. 本籍・戸籍

| カラム | 型 | 説明 |
|---|---|---|
| 本籍_町字 | TEXT | 本籍地の町字（`columns.json` の `honseki`） |
| 本籍_地番号または、街区符号 | TEXT | 地番号方式・街区符号方式のどちらかが入る（`columns.json` の `honseki_banchi`） |
| 戸籍_筆頭者_氏 / 戸籍_筆頭者_名 | TEXT | 筆頭者の姓・名（分割） |
| 戸籍_筆頭者 | TEXT | 筆頭者のフルネーム。`hub` は使わない（氏・名を結合して表示する） |

`hub` は本籍を `本籍_町字` + `本籍_地番号または、街区符号` の単純結合で表示する。地番号と街区符号を別カラムに持つ住民基本台帳システムもあるが、その場合はDB側のビュー等で1カラムに寄せるか、`columns.json` の `honseki_banchi` をどちらか一方に向けること。

筆頭者は `戸籍_筆頭者_氏` + 半角スペース + `戸籍_筆頭者_名` で組み立てる。フルネーム1カラムしか持たない場合は、`koseki_head_surname` にフルネーム列を、`koseki_head_given_name` に空列を割り当てる。

### 5-8. 転出先住所（確定）

| カラム | 型 | 説明 |
|---|---|---|
| 転出先住所（確定）_郵便番号 | TEXT | 7桁数字。**全角で格納される場合がある**（例: `１２３４５６７`） |
| 転出先住所（確定）_町字 | TEXT | 町字（丁目まで） |
| 転出先住所（確定）_番地号表記 | TEXT | 番地・号 |
| 転出先住所（確定）_方書 | TEXT | 方書（建物名・部屋番号等） |

完全な転出先住所は3カラムを結合して得る。

### 5-9. 必須カラムと任意カラム

検索・一覧表示に**必須**：

`宛名番号`・`世帯番号`・`氏名`・`氏名_フリガナ`・`生年月日`・`住民状態`・`住所_町字`・`住所_番地号表記`

世帯員一覧に必要：`続柄表記`・`記載順位`

詳細画面のみで使う**任意**（DBにない場合は空欄になる）：
住所系の残り・`性別表記`・`世帯主氏名`・`本籍`系・`戸籍_筆頭者`系

> **注意:** `columns.json` に書いた列がDBに存在しないとSQLエラーになる。**該当キーを `columns.json` から削除しても解決しない。** `lib/columns.ts` は書かれていないキーを既定値（芽室町の出力仕様準拠のカラム名）で補うため、削除するとむしろ既定のカラム名でSQLが組まれる。DB側にビューやダミー列を用意するのが確実。

## 6. 想定外・対象外

- 住民データの登録・更新・削除（`hub` は参照専用）
- 住民本人による利用（職員専用システム）
- インターネット経由での利用
- 住民基本台帳システムとのリアルタイム連携（住民データの投入方法は各自治体の運用による）
